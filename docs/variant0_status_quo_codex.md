# Variant 0 — status quo

### 0. Executive verdict (5–8 sentences)

Variant 0 preserves a ranking pipeline that is demonstrably useful: apply rate falls monotonically from 86.2% at ranks 1–5 to 14.3% at ranks 16–20, precision@10 is 0.90, and only 5 of 211 ranked-and-decided jobs (2.4%) are divergence cases ([snapshot lines 104–125](variant_analysis_data_snapshot_2026-10-19.md#L104)). It therefore avoids the quality and continuity risk of rebuilding a system whose final ordering is already strongly correlated with the candidate's decisions. It also preserves a specific scorer-calibration defect: all 7 dismissed cons point in the same direction, overvaluing Python or a Lead title for otherwise suitable PHP roles ([snapshot lines 71–92](variant_analysis_data_snapshot_2026-10-19.md#L71)). Its largest demonstrated inefficiency remains untouched: in a 500-item auto-reject sample, 393 (79%) incurred a full Sonnet score before rejection, while the free deterministic filter caught only 107 (21%) ([snapshot lines 24–38](variant_analysis_data_snapshot_2026-10-19.md#L24)). Its feedback loop also remains unusually sparse—11 signals from 209 decisions—and has not encoded that correction pattern ([snapshot lines 94–102](variant_analysis_data_snapshot_2026-10-19.md#L94)). There is no implementation or backfill cost, while steady-state cost remains approximately the present baseline (estimated about $1.90 for a typical 91-job run under today's cheaper Sonnet pricing, versus the recorded $2.25 historical run). I would recommend the status quo only as a conservative hold/baseline, not as the preferred long-term option: the ranking is not broken, but avoidable scoring spend and known user-specific errors are left knowingly in place.

### 1. Scope of change — is this evolution or revolution, concretely?

No pipeline files are touched, added, or deleted. In particular, `embeddings/indexer.py`, `embeddings/client.py`, `ranker/fusion.py`, `ranker/reranker.py`, `ranker/listwise.py`, `ranker/debate.py`, `ranker/rank_cache.py`, `evaluator/scorer.py`, `evaluator/dealbreakers.py`, `evaluator/profile.py`, `evaluator/runner.py`, `extractor/runner.py`, `scripts/rank_jobs.py`, `config.py`, and `evaluation/harness.py` remain byte-for-byte unchanged. The code delta is **0 added, 0 changed, 0 removed lines** (excluding this report).

The data model is the same: no new tables or columns, no migration, and no backfill. No historical job is re-embedded, re-extracted, or re-scored, so the one-off paid API cost is **$0**. For context, this avoids any greenfield backfill over the 5,359 jobs represented by the snapshot's status counts (1 + 1,178 + 76 + 221 + 3,783), but the snapshot does not provide per-job extraction and scoring token counts, so a defensible hypothetical full-backfill price cannot be derived from the $3.14-per-100 aggregate without assuming the same stage mix ([snapshot lines 9–22](variant_analysis_data_snapshot_2026-10-19.md#L9), [127–147](variant_analysis_data_snapshot_2026-10-19.md#L127)). The sibling `../JobAgentWeb` repository is not present in this worktree (`ls` returned “No such file or directory”), so its `embeddings_repo.py`, `migrations.py`, and `dedup_repo.py` could not be independently inspected; storage and dedup facts below therefore rely on the supplied production snapshot as instructed.

One-sentence verdict: **this is no change because it preserves every current module, execution stage, persisted representation, model call, and historical artifact.**

### 2. Strengths and weaknesses, explicitly relative to the OTHER two variants

**Relative to Variant 1 (evolution).** Variant 0 is better at preserving a measured, already-good ordering with zero rollout or prompt-regression risk: the current top-five bucket converts at 86.2%, `would_apply` precision is 0.80, and divergence is only 2.4% ([snapshot lines 104–125](variant_analysis_data_snapshot_2026-10-19.md#L104)). It is worse because it declines process-only fixes that directly match observed failures: it keeps paying Sonnet for the 79% share of sampled auto-rejects missed by deterministic filtering, does not turn dismissals into prompt/profile corrections, and does not add spoken-language or longer-horizon cross-country duplicate checks. What is lost by not evolving is therefore concrete: potential scorer-call savings on a large, observed rejection class and correction of a 7-for-7 bias, without needing a schema reset. The snapshot does not split the $1.05 historical Sonnet scorer-plus-debate cost by component or state how many of a typical day's jobs become auto-rejects, so the attainable daily dollar saving cannot honestly be calculated from current evidence.

**Relative to Variant 2 (revolution).** Variant 0 is better at retaining all current behavior and learned state with no cold start, migration, backfill, or validation period. That matters because current multi-stage ranking combines semantic history, scorer rank, reranking, listwise comparison, debate, exploration, and caching (`scripts/rank_jobs.py:75-185`) and already produces strong behavioral separation. It is worse because it retains the limits of the current representations and feedback loop: embeddings use title, company, location, and at most 2,000 excerpt characters (`embeddings/indexer.py:26-33`); learned preferences yielded only 11 signals from 209 decisions; and recurring duplicates and explicit spoken-language requirements are not modeled as first-class rejection patterns. What is lost by not rebuilding is the opportunity to design extraction, storage, deduplication, and preference learning coherently around those observed categories—but there is no evidence that infrastructure replacement alone would improve the already-strong rank-bucket curve, and a reset would initially discard useful personalization.

### 3. Matching-quality analysis, grounded in real behavior

**What is already working.** The best evidence is behavioral rather than architectural. Apply rate is 86.2% for ranks 1–5 (n=29), 45.0% for 6–10 (n=20), 38.1% for 11–15 (n=21), and 14.3% for 16–20 (n=7); precision@5 is 0.80 and precision@10 is 0.90 ([snapshot lines 104–117](variant_analysis_data_snapshot_2026-10-19.md#L104)). The `would_apply` gate has 0.80 precision among 20 decided flags, and only 5/211 ranked-and-decided jobs meet the deliberately extreme divergence definition ([snapshot lines 119–125](variant_analysis_data_snapshot_2026-10-19.md#L119)). These samples are not large—especially the rank-16–20 bucket—and precision@5/@10 cover only the latest 5/10 decisions, but all reported measures point toward useful ordering, not a generally failed matcher.

The implementation plausibly supports that result. Similarity uses maximum proximity to any applied job and subtracts 0.3 times proximity to rejected history rather than collapsing multiple interests into one centroid (`embeddings/indexer.py:92-128`). Reciprocal-rank fusion combines embedding and LLM ranks, with an optional reliable reranker leg (`ranker/fusion.py:13-55`); the active pool is fused, reranked to 50, then listwise-ranked to 20 (`scripts/rank_jobs.py:94-154`, `config.py:35-39`). The listwise model sees the scorer rating and breakdown, is shown jobs in shuffled order to reduce position anchoring, and must rank every item (`ranker/listwise.py:55-98`, `ranker/listwise.py:165-202`). Debate is deliberately a bounded second opinion: dealbreaker risks go to the bottom and softer disagreements move only three positions (`ranker/debate.py:25-30`, `ranker/debate.py:190-227`). Unchanged, non-degraded results are cached rather than paying for repeated Opus/debate work (`ranker/rank_cache.py:8-32`).

**What remains wrong.** First, the 7 dismissed-item corrections are small in number but perfectly consistent: the scorer treats absent Python/AI tooling or an absent Lead title—and in three Kempuri corrections, Magento/agency assumptions—as meaningful cons despite the candidate explicitly saying they are not. The scorer prompt gives the learned profile precedence over generic preferences but contains no mechanism that directly consumes dismissed cons (`evaluator/scorer.py:63-100`, `evaluator/scorer.py:123-175`). Variant 0 therefore does not correct this bias. Because the scorer participates in RRF before shortlist truncation (`ranker/fusion.py:13-55`, `scripts/rank_jobs.py:94-110`) and its rating is shown to the listwise model (`ranker/listwise.py:77-98`), a biased score can influence both admission to and ordering within the shortlist even if later stages sometimes compensate.

Second, preference learning is too sparse to claim it closes the loop: 68 applied plus 141 rejected decisions produced only 11 signals, about one per 19 decisions, and the observed Python/Lead correction did not surface ([snapshot lines 94–102](variant_analysis_data_snapshot_2026-10-19.md#L94)). The evaluator does feed up to 10 extreme ranking divergences into the scoring prompt (`evaluator/runner.py:14-16`, `evaluator/runner.py:75-82`), but the divergence definition catches only top-5 rejects or rank-16+ applies; it is not the same as a user dismissing an individual con. Low 2.4% divergence is evidence of good gross ordering, not evidence that explanations and preference calibration are correct.

Third, deterministic rejection has incomplete coverage. It checks trusted extracted values for salary, remote/hybrid, geography, seniority, company type, company working language, and salary disclosure (`evaluator/dealbreakers.py:230-293`). Its language check recognizes only the extracted company's `working_language` values Polish/English (`evaluator/dealbreakers.py:201-219`), not explicit requirements such as C1 German or French fluency in a description. It has no cross-posting identity check. The production evidence shows both omissions matter: 7+ country-mirror duplicates in just the supplied rejection-reason sample, plus French, German, Spanish, and Russia-related language cases ([snapshot lines 40–69](variant_analysis_data_snapshot_2026-10-19.md#L40)).

Fourth, filtering happens before scoring, but catches only 21% of eventual auto-rejects in the 500-job sample; the other 393 receive a Sonnet call and are then rejected at score ≤1 ([snapshot lines 24–38](variant_analysis_data_snapshot_2026-10-19.md#L24)). The code confirms the order and cost boundary: `apply_dealbreaker_filter` runs first (`evaluator/runner.py:41-56`), every survivor needing a fresh fingerprint is passed individually to `score_job` (`evaluator/runner.py:84-120`), and the threshold is 1.0 (`config.py:17-20`). This is principally an efficiency problem; the snapshot does not demonstrate that those 393 decisions were wrong.

**New failure modes.** Variant 0 introduces no new code-path failure mode because it changes nothing. Its risk is continued exposure and drift: known calibration errors keep influencing scorer/RRF/listwise inputs, recurrent duplicates and language requirements keep reaching the user or paid scorer, and the evidence base for operational cost is stale because no run summaries were recorded after 2026-08-30 ([snapshot lines 127–141](variant_analysis_data_snapshot_2026-10-19.md#L127)).

### 4. User-behavior grounding (explicit, not implicit)

**The 7 dismissed-item cases:** they are treated no differently. Variant 0 neither injects dismissals into the scorer prompt nor converts them into a direct preference signal. Similar future PHP-core jobs can still lose credit for no Python/AI tooling, no Lead/architect title, Magento, or an agency/e-commerce context, notwithstanding the candidate's seven corrections ([snapshot lines 71–92](variant_analysis_data_snapshot_2026-10-19.md#L71)).

**“Duplicate posting, different country, already applied” (7+ occurrences):** it is treated no differently. There is no check in `evaluator/dealbreakers.py:230-293`; according to the production snapshot, JobAgentWeb's separate deduplication uses confidence 0.60 and a 21-day window, which is too short for the across-month pattern ([snapshot lines 60–69](variant_analysis_data_snapshot_2026-10-19.md#L60)). The sibling repository was unavailable, so that server-side implementation could not be independently verified here. Such a mirror can therefore remain a separate candidate, consume extraction/scoring/ranking work, and require another manual rejection.

**Required spoken language:** it is treated no differently. Candidate languages are rendered into the questionnaire (`evaluator/profile.py:94-107`), so an LLM may notice a conflict, and the debate prompt asks for explicit unmet requirements (`ranker/debate.py:137-150`); neither is a deterministic guarantee. The free filter only compares candidate language codes to `working_language`, not to a required-language field (`evaluator/dealbreakers.py:201-219`). Consequently, explicit French fluency, C1 German, or a Spanish-language offer can still survive deterministic filtering and be handled later at paid scoring or by the human, exactly as the rejection sample demonstrates ([snapshot lines 40–57](variant_analysis_data_snapshot_2026-10-19.md#L40)).

### 5. Cost analysis — two separate numbers, not one blended estimate

**(a) One-time implementation cost.** Assuming one engineer and treating preparation of this diagnostic as analysis rather than implementation, engineering effort is **0 hours**, code delta is zero, and one-off paid API spend is **$0**. There is no migration, re-embedding, re-extraction, or re-scoring. This is the principal economic strength of Variant 0.

**(b) Ongoing day-to-day operational cost.** The recorded baseline is about **$2.25 per typical 91-job run** and **$3.14 per 100 jobs** across the historical accounting window; the example run spent $0.86 on Haiku extraction, $1.05 on Sonnet scorer+debate, $0.33 on Opus, $0.0014 on reranking, and $0.003 on embedding ([snapshot lines 127–147](variant_analysis_data_snapshot_2026-10-19.md#L127)). Variant 0 changes no call volume, so it saves **$0 versus today's status quo**. For a like-for-like 91-job run under today's `claude-sonnet-5` rates, a reasonable estimate is **about $1.90**: the historical Sonnet 4.6 component scales from $1.05 to roughly $0.70 because both listed input and output rates fall by one third (`config.py:63-72`), leaving the other $1.20 unchanged. This is an estimate, not a newly observed run—the run-summary gap after 2026-08-30 prevents direct validation, prompt caching and token mix can vary, and the $1.05 combines scorer with debate. On days whose candidate set is unchanged, the cache can make the run much cheaper (the recorded minimum is $0.0072), while catch-up volume can make it much higher (recorded maximum $4.24), so “per day” should be read as one typical daily run, not a fixed bill.

The opportunity cost is material but cannot be reduced to an honest exact dollar figure from the snapshot. Among sampled auto-rejects, 79% pay for Sonnet before being discarded, and scoring/extraction—not embeddings or reranking—dominate the bill. Variant 0 captures none of the possible saving, but it would be invalid to multiply 79% by the full $1.05 Sonnet line: 79% is conditional on auto-rejects, the typical run's auto-reject count is not reported, and that line includes debate. Likewise, replacing vector storage would target only about $0.0044 of the typical run's embedding-plus-rerank cost and would not address any documented quality failure.
