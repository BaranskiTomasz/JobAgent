# Variant 2 — revolution

### 0. Executive verdict (5–8 sentences)

I recommend a greenfield rebuild, but only as an instrumented replacement run in shadow mode until it matches the current system's already-strong ranking baseline: 86.2% apply rate at ranks 1–5, 0.80 precision@5, 0.90 precision@10, and only 5/211 (2.4%) divergent ranked decisions (`docs/variant_analysis_data_snapshot_2026-10-19.md` §6). For matching quality, the main gain is not a fashionable vector store; it is an evidence-backed job fact model, deterministic identity/language/eligibility gates, and a preference model trained from explicit pairwise judgments plus outcome feedback. That should directly address all seven dismissed-cons corrections, the 7+ country-mirror duplicates, mandatory spoken-language misses, and the current yield of only 11 signals from 209 decisions (snapshot §§3–5). The likely steady-state quality is better calibrated rather than dramatically higher, because the present ranker is already good and the sample is small. The one-time rebuild is substantial—about 20–30 engineer-days and roughly $50–$165 of model backfill spend, depending on whether only extraction is rerun or the historical full pipeline is replayed—but ongoing cost should fall from the historical ~$2.25 typical run to about $0.85. The learning/CV value is independently strong: implementing provenance-aware extraction, hybrid retrieval, active preference learning, counterfactual evaluation, and calibrated learning-to-rank is a credible modern ranking/RAG story; I recommend the experimentation and evaluation machinery partly for that reason, even where it may not immediately improve matching. A hard cutover is not recommended: wiping the 209-decision profile creates a real cold-start regression, so promote the rebuild only after offline replay plus several weeks of shadow comparison.

### 1. Scope of change — is this evolution or revolution, concretely?

The rebuild keeps raw collected descriptions as its fixed input and replaces everything downstream. Existing entry points would be rewritten or retired: `extractor/runner.py`, `embeddings/indexer.py`, `embeddings/client.py`, `ranker/fusion.py`, `ranker/reranker.py`, `ranker/listwise.py`, `ranker/debate.py`, `evaluator/scorer.py`, `evaluator/dealbreakers.py`, `evaluator/profile.py`, `scripts/rank_jobs.py`, and ranking/extraction portions of `config.py`. New modules would cover canonical job identity, schema-versioned fact extraction with evidence, hard-constraint evaluation, hybrid lexical/dense retrieval, feature construction, pairwise preference elicitation, a calibrated ranking model, and offline/shadow evaluation. I estimate roughly 2,500–3,500 added lines, 900–1,300 changed lines, and 1,500–2,000 removed lines; this is a planning range, not a measured diff.

The data model changes. I would add normalized, versioned tables for `job_facts` and field provenance; `job_identity_clusters` and cluster membership; `candidate_constraints`; atomic `preference_observations` (explicit answers, pairwise choices, applies, rejects, dismissals); model/versioned `job_features`; and `ranking_impressions` with candidate set, rank, propensity/exploration marker, and later outcome. Embeddings should live as a native vector column/index in the existing PostgreSQL deployment if available, while lexical search uses PostgreSQL full-text search; a dedicated vector database is unjustified for the observed active-pool cap of 2,000 (`scripts/rank_jobs.py:51-57`) and embedding/rerank spend of only ~$0.0044 in the representative run (snapshot §7). This requires migrations and backfills, with dual-write/shadow tables during validation.

All 5,259 historical rows in the snapshot (1 new + 1,178 reviewed + 76 applied + 221 rejected + 3,783 auto-rejected) should be re-extracted from their retained raw text, deduplicated, featurized, and embedded; no re-scraping is assumed. Snapshot §7 gives no isolated all-history extraction price, so the defensible bounds are: about **$49.70** for extraction alone by extrapolating run 12's $0.86/91 jobs to 5,259 jobs; about **$0.17** for embeddings by extrapolating $0.003/91; or **$165.13** for a full historical replay at the system's blended $3.14/100 jobs. Re-scoring every historical row is unnecessary: labels and fact features can train/evaluate the first model, while a stratified adjudication sample can be rescored. These are linear estimates from one representative run or the historical blended metric, not vendor-list-price claims, and extraction complexity may differ across old descriptions.

**Verdict: this is a revolution because it changes the schema, preference data, job identity, extraction, retrieval, ranking, evaluation, and user interaction rather than tuning the current prompts.**

### 2. Strengths and weaknesses, explicitly relative to the OTHER two variants

Relative to **Variant 0 (status quo)**, Variant 2 is better at turning observed errors into durable data: required spoken language becomes an extracted hard constraint, mirrors become identity clusters, and “Python/Lead absence is not a con” becomes explicit preference evidence instead of hoping the scorer infers it. It is worse in migration risk, engineering cost, and initial personalization: Variant 0 preserves a pipeline whose rank buckets already strongly correlate with applying and whose divergence is only 2.4% (snapshot §6), while Variant 2 initially discards 209 decisions' distilled state.

Relative to **Variant 1 (evolution)**, Variant 2 is better at attribution and learning: impression logs, atomic labels, versioned features, and pairwise choices permit offline comparisons and calibrated models rather than entangling extraction, scoring, RRF, Opus ranking, and debate. It is worse in time-to-value and likely marginal return: Variant 1 can cheaply add language/duplicate filters and correct the Python/title prompt bias while preserving the proven ranking, whereas Variant 2 needs weeks of build and shadow validation to establish that its broader redesign is not a regression.

### 3. Matching-quality analysis, grounded in real behavior

The current pipeline is not broken. Its apply rate falls monotonically from 86.2% at ranks 1–5 (n=29), through 45.0% and 38.1%, to 14.3% at ranks 16–20 (n=7); precision@5 is 0.80, precision@10 is 0.90, `would_apply` precision is 16/20 = 0.80, and only 5 of 211 ranked decisions diverged (snapshot §6). Those sample sizes are limited, and “apply” is not eventual job success, but they set a high replacement bar.

The redesigned path is: canonicalize/deduplicate first; extract evidence-linked facts once; apply high-confidence hard constraints; retrieve broadly with lexical plus dense signals; then rank survivors using transparent features and a calibrated pairwise/listwise model. A small LLM should adjudicate only uncertain or top-candidate cases, not score every survivor independently. This removes the current ordering dependency in which expensive per-job scoring precedes shortlist ranking (`evaluator/scorer.py:230-280`; `scripts/rank_jobs.py:94-129`) and makes the decision explainable as constraints plus learned utilities.

It directly fixes the known problems:

- The seven dismissed corrections are stored as seven explicit negative labels on proposed penalties. The feature model distinguishes **core required PHP** from **optional Python** and treats title as weak evidence for responsibility level, so missing Python or “Lead” cannot lower a PHP-core role unless the candidate explicitly reverses that preference. This is stronger than the present free-text learned profile, which produced only 11 signals from 209 decisions and did not absorb a 7/7-consistent correction pattern (snapshot §§4–5).
- Mirror duplicates are clustered using normalized company, role, description fingerprints, requirements, and source IDs without the current external 21-day limitation. Ranking operates on clusters, suppresses any cluster containing an applied posting, and shows one representative when unseen. This targets the 7+ duplicate rejections in the 25-reason sample (snapshot §3).
- Extraction includes per-language requirement level and evidence span, then compares required spoken languages with candidate proficiency before paid ranking. The current extractor already has a `languages` structure (`extractor/runner.py:193-205`), but the deterministic filter checks only the coarse `working_language` enum (`evaluator/dealbreakers.py:201-219,269-284`); the redesign connects the richer fact to enforcement.
- The deterministic tier should catch materially more than today's 107/500 (21%) sampled auto-rejects before Sonnet. The observed 393/500 LLM-score auto-rejects are an upper bound, not all safely deterministic; a labeled audit must establish coverage and false-reject rate before expanding gates (snapshot §2).

What remains untouched or uncertain: no architecture can recover requirements absent from the retained raw text, and no re-scraping means truncated/stale descriptions remain truncated/stale. It also cannot infer market salary competitiveness because the snapshot contains no live market benchmark (§8). “Applied” is a choice label affected by what was shown, timing, and duplicate exposure—not a clean relevance judgment—so it must not be treated as objective ground truth.

New failure modes include extraction errors becoming hard filters, identity clustering incorrectly merging different roles, active-learning questions annoying the user, and a learned model amplifying exposure bias. Mitigations are evidence-required hard rejects with fail-open behavior, reversible cluster membership, confidence thresholds, capped questioning, randomized exploration, complete impression logging, and shadow evaluation against the current ranker. The current extractor's evidence/confidence approach (`extractor/runner.py:285-300,653-672`) is worth preserving conceptually even though the schema is rebuilt.

### 4. User-behavior grounding (explicit, not implicit)

For the **seven dismissed-item cases**, each dismissal becomes an atomic correction tied to a feature and explanation: optional Python absence and non-Lead titles receive zero penalty. Those corrections apply immediately to rescoring and seed pairwise questions such as “same PHP fit: Senior Engineer without Python versus Lead role with weaker PHP—which would you apply to?” The system does not generalize the Magento/agency dismissals into universal preferences after one observation; it asks a targeted confirmation or treats them as low-confidence indifference.

For **“duplicate posting, different country, already applied”**, canonical identity is resolved before candidate scoring. If any member of a cluster is applied, every country/source mirror is hidden as already handled; if none is handled, one best-supported eligible representative is ranked. Ambiguous merges remain visible with a “possible duplicate” marker instead of being silently removed.

For **required spoken language**, extraction records language, minimum level, required/preferred status, and supporting span. A high-confidence unmet required language rejects before LLM scoring; uncertain wording fails open and is surfaced as a risk. This differs from the current check, which can reject on company working language but cannot enforce description-level French/German/Spanish requirements (`evaluator/dealbreakers.py:201-219`). A separate explicit geopolitical/company exclusion represents the reported Russia-related rejection rather than misusing language as a proxy.

### 5. Cost analysis — two separate numbers, not one blended estimate

**(a) One-time implementation cost.** Assuming one experienced engineer assisted by coding tools, I estimate **20–30 engineer-days (160–240 hours)**: 4–6 days for schemas/migrations/backfill; 4–5 for extraction, evidence, and identity clustering; 4–5 for elicitation/profile UX; 4–6 for retrieval/ranking; and 4–8 for evaluation, shadow operation, tests, and cutover tooling. The paid backfill is approximately **$49.70 extraction + $0.17 embedding**, extrapolated from run 12 to 5,259 rows; budget **up to $165.13** if the full pipeline is replayed at the real $3.14/100 blended rate (snapshot §7). Re-adjudicating a stratified sample would add an unknown amount because the snapshot provides no per-call figure for the proposed models; it should be metered, not invented.

**(b) Ongoing day-to-day operational cost.** I estimate **~$0.85 per typical 91-job run**, versus the historical **$2.25**. The design keeps extraction roughly at the historical $0.86/91-job level as a conservative assumption, makes native lexical/vector retrieval negligible, removes routine Sonnet scoring of every job, and invokes an LLM only for uncertain top cases; the saved leg is most of the historical $1.05 Sonnet spend plus the $0.33 Opus component, partly offset by selective adjudication. A plausible range is $0.70–$1.10 until measured. The estimate deliberately targets extraction/scoring, which were $1.91/$2.25 (85%) in run 12, rather than optimizing embeddings and reranking that together cost ~$0.0044; current Sonnet 5 pricing also means the historical baseline slightly overstates today's scorer cost (snapshot §7).

### 6. (Variant 2 ONLY — skip this section if you're writing variant 0 or 1)

**Collection from retained raw text.** Collection becomes cluster-first and decision-aware. Every old and new raw description is normalized, language-detected, fingerprinted, and attached to a canonical posting cluster before expensive processing; source/country mirrors enrich one entity rather than occupy several ranking slots. Query/source yield is measured at the cluster level so seven mirrors do not look like seven opportunities, and searches producing only ineligible or duplicate clusters can be pruned. This improves useful collection without assuming historical re-scraping; what is lost is any field absent from the stored text or source metadata, and false cluster merges require an undo path.

**Extraction schema.** Replace the broad JSON blob with versioned facts for role family and responsibility level; skills with required/preferred/alternative and minimum years; work mode, office cadence, country/residency/work-authorization eligibility; contract and normalized compensation; required/preferred spoken language and level; company/industry; and completeness. Every fact carries source span, extractor/model version, confidence, and source-native versus inferred provenance. This builds on the good ideas already visible in the current schema—skills, compensation bands, country eligibility, languages, and evidence (`extractor/runner.py:126-227`)—but makes them queryable and actually connects them to constraints. Matching quality, not résumé optics, is the primary reason.

**Preference-profile bootstrap.** On day one, ask a 10–15 minute structured questionnaire separating hard constraints from soft utilities: remote geography and office cadence, authorization, salary/contract floor, spoken languages, PHP-central versus adjacent roles, acceptable seniority/responsibility, management appetite, industries/company modes, and explicit indifferences such as “Python is nice-to-have” and “Engineer title is acceptable.” Then present **12–20 diverse pairwise choices**, selected to isolate one or two trade-offs and including “both,” “neither,” and “unsure”; do not ask the user to score arbitrary 0–10 scales. Fit a regularized utility model with uncertainty, seed it with questionnaire priors, and ask at most 2–3 high-information comparisons per review session until rankings stabilize. Log applications, rejections with structured reason chips plus optional text, dismissals, skips, and impressions separately; never equate non-click with rejection.

This bootstrap should be useful immediately for hard constraints and obvious PHP-core relevance, but nuanced personalization has a real delay. The old system saw 209 decisions over “several months,” roughly 1 signal per 19 decisions (snapshot §5); if “several” means 3–6 months, the historical pace is about **8–17 decisions/week**. A 12–20-pair bootstrap therefore supplies approximately 1–2.5 historical weeks of preference choices in one session, though synthetic comparisons are not equivalent to real applications. I estimate **2–4 weeks** to become practically useful after 25–50 real decisions and **8–12 weeks** to approach the behavioral evidence of 100–150 decisions; matching all 209 organic decisions would still take roughly **12–26 weeks** at that inferred pace. These ranges are explicit assumptions because the snapshot gives neither exact elapsed months nor weekly decision counts. The wipe therefore loses months of organic behavioral evidence and risks preference fatigue; retain the old outcomes only as a frozen evaluation set, not as live profile state, to respect the reset while measuring regression.

**Embedding/retrieval layer.** Index two representations per canonical cluster: full normalized description chunks for evidence retrieval and a compact extracted “job card” for candidate matching. Use PostgreSQL full-text/BM25-like lexical ranking plus dense embeddings, fuse ranks, and apply cross-encoder reranking only to a modest survivor set after constraints. At an active pool capped at 2,000 (`scripts/rank_jobs.py:51-57`), exact or PostgreSQL-native vector search is operationally sufficient; a separate vector service has no quality or cost justification in the snapshot. Dense retrieval helps semantic recall, lexical retrieval protects exact must-have terms such as PHP/Symfony and explicit language levels, and structured constraints handle negation rather than asking embeddings to understand it—the current profile code itself warns that bare avoided-tech terms can reverse intent (`evaluator/profile.py:11-18`).

**Learning-value boundary.** Building logged impressions, active pairwise learning, calibrated rank evaluation, provenance, hybrid retrieval, and shadow experiments is recommended both for system quality and because it creates an honest modern search/ranking portfolio story. Using a dedicated vector database, distributed ANN, or an elaborate deep ranker would be mainly résumé theatre at 2,000 active jobs and is not recommended. The strongest interview story is the measured decision to avoid unnecessary infrastructure, reproduce the existing 0.80/0.90 precision baseline, and demonstrate which redesign elements improve calibration or cost through ablations.
