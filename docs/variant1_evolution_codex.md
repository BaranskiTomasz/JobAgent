### 0. Executive verdict (5–8 sentences)

Variant 1 should be implemented as a measured process evolution, because the current system already ranks decided jobs well—86.2% apply rate at ranks 1–5, `precision_at_5=0.80`, `precision_at_10=0.90`, and only 5/211 (2.4%) divergence cases—while wasting paid scoring and repeating a narrow, demonstrated calibration error (snapshot §§4, 6). The highest-confidence quality changes are to make explicit required spoken languages and high-confidence country-mirror duplicates deterministic pre-score gates, tell the scorer that absence of optional Python and a Lead title is neutral for PHP-core roles, and force preference distillation to preserve direct corrections rather than letting them disappear into an 11-signal profile. A structured-facet score over facts already in `structured_data` should become the existing RRF's first-pass `extra_rank_field`, but only if a frozen replay shows higher recall@50 without degrading the strong rank-bucket curve. Full-description embeddings are a sensible small repair to the current 2,000-character truncation, not a reason to change the JSON-text vector storage. I would ablate debate before changing its provider: it is already secondary to Opus and cached, and no production evidence attributes an error or benefit specifically to that stage. The likely steady-state cost falls from the historical ~$2.25 typical run to about **$1.90**, with a plausible $1.75–$2.05 range, but the snapshot does not expose enough per-run rejection-category counts to claim a tighter number. I recommend this variant because it targets every observed user correction with reversible logic while preserving the proven ranking cascade and storage contract.

### 1. Scope of change — is this evolution or revolution, concretely?

The proposed implementation is approximately **450–700 added/changed lines and no deleted subsystem**, spread across:

- `evaluation/harness.py` (about 150–250 lines): add a read-only, frozen replay command and stage metrics—dealbreaker false-positive/false-negative rate, recall@50 before Voyage, nDCG@10, P@5/P@10, and cost per surfaced applied job. The current file is only a proxy for `/api/eval/report` (`evaluation/harness.py:5-17`), so it cannot attribute lift to filtering, fusion, listwise, or debate.
- `evaluator/dealbreakers.py` (about 90–140 lines): add fail-open checks for explicit required job languages and conservative duplicate mirrors before Sonnet. Today it admits only high-confidence structured fields (`evaluator/dealbreakers.py:24-26`) and checks company `working_language`, not a job requirement (`evaluator/dealbreakers.py:201-219, 269-293`).
- A small new helper such as `evaluator/pre_score_signals.py` (about 80–120 lines): normalize company/title, strip location boilerplate, compute description shingles or SimHash in memory, and compare the current pool with already-fetched applied/rejected examples. No result is persisted.
- `evaluator/scorer.py` and `evaluator/runner.py` (about 35–60 lines): add explicit calibration rules and dismissed-factor examples. The prompt currently says only how to weight criteria and salary (`evaluator/scorer.py:152-175`), while the runner includes divergence cases but not dismissals (`evaluator/runner.py:70-82`).
- `preference_agent/runner.py` / `preference_agent/profile.py` (about 50–90 lines): make direct corrections mandatory structured signals, separate stable direct corrections from conservative behavioral inference, report coverage by dimension, and sample rejection-reason strata instead of only the 50 most recent applied and 50 most recent rejected jobs (`preference_agent/runner.py:100-107, 169-205`). The current prompt already calls dismissals the strongest evidence (`preference_agent/runner.py:59-63`), but the output schema requires only `type` and `dim` (`preference_agent/profile.py:1-48`), so a model can still omit the correction.
- `ranker/fusion.py` plus a new `ranker/facet_score.py` and `scripts/rank_jobs.py` (about 70–110 lines): compute a deterministic facet rank from required/core PHP overlap, required-skill coverage, seniority compatibility, remote/eligibility, and explicit language compatibility, then pass it as `extra_rank_field` in the **first** RRF at `scripts/rank_jobs.py:104-110`. The second fusion continues using `rerank_score` (`scripts/rank_jobs.py:117-120`); `fuse_by_rrf` already supports exactly this extension (`ranker/fusion.py:13-21, 44-53`).
- `embeddings/indexer.py` (about 5–15 lines): replace `excerpt[:2000]` (`embeddings/indexer.py:26-33`) with the same normalized excerpt seen by downstream stages, retaining one 1,024-dimensional JSON-text vector and the existing `text_hash` invalidation.
- Tests/fixtures (about 100–180 lines) for language negation, “nice to have” language wording, multilingual postings, duplicate mirrors, PHP/Python calibration, and RRF ablations. `config.py` may gain thresholds but models need not change initially.

**Data model and storage remain exactly the same:** same Postgres tables, same columns, same one-vector JSON-text embedding representation, no migration, no new database, and no vector index. Existing extractor JSON already has a `languages` array with `required/preferred/working_language` and evidence (`extractor/runner.py:193-205`), so this process can consume that field without a column change. Language facts are currently medium-confidence by default because `_EVIDENCE_BACKED_DEALBREAKER_FIELDS` omits `languages` (`extractor/runner.py:270-300`); the process change should accept only explicit evidence from each language item, or a tightly scoped raw-text pattern, and otherwise fail open.

No historical re-extraction or re-scoring is required. Active embeddings should be regenerated once because their text hashes change; at the 2,000-job safety cap (`scripts/rank_jobs.py:51-57`), extrapolating the snapshot's actual $0.003 for 91 embeddings gives ~$0.066 at the old text length and roughly **$0.10–$0.25** for longer inputs, not an invented list-price estimate. A frozen evaluation can reuse stored facts, scores, and vectors; budget **$5–$15** only if several 200-job challenger runs deliberately call Sonnet/Opus again. Old rows with no language evidence fail open, so a full extraction backfill is neither necessary nor safe to assume. The adjacent `../JobAgentWeb` directory was not present in this worktree, so I could not verify `embeddings_repo.py` or `migrations.py` directly and rely on the supplied snapshot for storage facts.

**Verdict:** this is an evolution because it changes gates, prompts, evaluation, representations, and fusion legs while preserving every table, column, storage technology, and downstream ranking stage.

### 2. Strengths and weaknesses, explicitly relative to the OTHER two variants

Relative to **Variant 0 (status quo)**, Variant 1 is better because it directly addresses all four observed failures: paid Sonnet calls after cheaply detectable exclusions, the 7/7 Python/Lead false-cons pattern, uncaught language and duplicate rejections, and the sparse 11/209 preference yield. It is worse because the status quo has zero implementation risk and already has strong behavioral ranking evidence; new regexes, duplicate similarity, facet weights, and prompts can create false rejects or disturb a rank curve that currently drops cleanly from 86.2% applied at ranks 1–5 to 14.3% at ranks 16–20 (snapshot §6).

Relative to **Variant 2 (revolution)**, Variant 1 is better because it preserves 209 decisions, existing extracted JSON, cached scores/ranks, and a production-proven cascade, avoiding a cold start and a large migration/backfill. It is worse because it must work around legacy facts of uneven confidence, one embedding representation per job, exposure-biased labels, and the existing API/storage contract; a clean redesign could model explicit language requirements, canonical posting identity, and preference provenance as first-class typed data. Under the hard constraint, those limitations are acceptable because the current 2.4% divergence rate gives no evidence that a storage reset would repay its risk.

### 3. Matching-quality analysis, grounded in real behavior

The baseline is good but not uniformly calibrated. The 1–5/6–10/11–15/16–20 apply rates are 86.2%/45.0%/38.1%/14.3% (n=29/20/21/7), `would_apply` precision is 16/20=0.80, and only 5 of 211 ranked-and-decided jobs diverge at the defined extremes (snapshot §6). Therefore this proposal does **not** replace max-sim retrieval, RRF, Voyage, Opus, or caching: embeddings use max applied similarity minus 0.3× rejected similarity (`embeddings/indexer.py:92-128`), RRF avoids mixing incompatible score scales (`ranker/fusion.py:13-53`), and unchanged candidate sets already reuse listwise/debate results (`ranker/rank_cache.py:15-32`). Every new ranking signal must beat that baseline on held-out, time-split replay—not merely move offline IDs.

**Pre-score filtering and the 79% waste.** In a 500-auto-reject sample, 393 (79%) reached Sonnet and were discarded only at score ≤1; deterministic seniority/salary/company/work-mode checks caught 107 (21%) first (snapshot §2). It would be unsafe to convert the entire scorer's “poor fit” judgment into regexes. Instead, extend only high-precision constraints already confirmed by behavior:

1. Reject an explicit required spoken language only when the candidate lacks that language at working level and the posting supplies evidence such as “C1 German required” or “fluent French mandatory”; ignore “nice to have,” ambiguous language-of-posting, and English. This uses existing questionnaire languages (`evaluator/profile.py:94-99`) and existing job JSON, with raw description as a conservative fallback.
2. Reject a country mirror only when a normalized company+role matches and near-identical substantive description text is found in a previously applied posting; strip location/legal boilerplate first and require a very high similarity threshold. If the earlier match was merely rejected, mark/downrank rather than auto-reject unless its reason explicitly says duplicate.
3. Add measured, evidence-backed regex gates for the already recurring authorization/residency phrases in snapshot §3, but only after the replay quantifies precision. Do not generalize the scorer's broad stack-fit failures into hard gates.

This will catch some of the 79%, not all. The snapshot provides rejection-reason occurrences but not how many of the 393 low-score jobs belong to these categories, so a defensible savings claim must remain a range until instrumentation records `pre_filter_reason` counts. The new harness should shadow the rules for two weeks, report how many Sonnet calls each would avoid and manually audit false positives before enabling rejection.

**The 7/7 PHP calibration error.** All seven dismissed score factors point in the same direction: the scorer turned an optional or irrelevant attribute of an otherwise suitable PHP role into a con; four explicitly concern absent Python or an absent “Lead” title, while the other two Magento entries and the agency/e-commerce entry reinforce the broader over-penalization pattern (snapshot §4). The scorer prompt should state: “For a PHP-core role, absent Python/AI and an Engineer/Senior rather than Lead title are neutral unless a direct current preference makes them mandatory; never list absence as a con. Evaluate actual scope, not title token.” The tool schema's `cons` description should enforce that rule (`evaluator/scorer.py:207-216`), and the listwise/debate prompts should receive the same calibration so they do not reintroduce it. This is a prompt/preference-weighting correction, not infrastructure. It risks underweighting genuinely Python-centric ambitions, so scope it to PHP-core roles and preserve direct questionnaire precedence, which already outranks learned preferences (`evaluator/scorer.py:63-82`).

**Sparse preference profile.** Eleven signals from 68 applied + 141 rejected decisions—one per ~19 decisions—is too sparse given the repeated reasons and seven direct corrections (snapshot §5). Part of this is sampling: distillation sees at most the 50 most recent items in each class even though totals drive the header (`preference_agent/runner.py:100-107, 169-205`). Part is an output-contract problem: “one signal per dimension” plus only eight allowed dimensions encourages compression, and validation does not require value/confidence/evidence counts (`preference_agent/runner.py:65-78`; `preference_agent/profile.py:25-44`). Fix it by stratifying examples across reason clusters and time, requiring coverage accounting for each dimension, emitting distinct sub-values when behavior differs, and deterministically injecting direct dismissed corrections as HIGH signals if the distiller omits them. More signals are not automatically better: accept a signal only with quoted/referenced evidence, keep contradictory or weak dimensions neutral, cap prompt-rendered signals by confidence/recency, and evaluate score calibration before/after. This converts “conservative” from silent omission into observable abstention.

**Structured-facet RRF and embedding repair.** The extractor already stores core/required/preferred skills, seniority ranges, languages, and eligibility (`extractor/runner.py:126-205`), but first-pass fusion uses only embedding rank and Sonnet score (`scripts/rank_jobs.py:104-110`). A deterministic facet score can reward PHP/Symfony core fit and required-skill coverage without making them hard filters, using the existing `extra_rank_field`; this is especially appropriate because “PHP entirely absent” appeared four times in the 25-reason sample (snapshot §3). It should not include soft company stereotypes or treat missing facts as zero. Separately, full-description embedding removes a credible recall blind spot before the top-50 gate, since only the first 2,000 characters are embedded while reranking and listwise see the longer excerpt (`embeddings/indexer.py:26-33`; `ranker/reranker.py:44-52`; `ranker/listwise.py:120-123`). Neither improvement is proven by the current aggregate metrics, so promotion requires higher held-out recall@50 and non-inferior nDCG/P@k.

**New failure modes and controls.** False language rejection can come from negation, optional requirements, or describing a customer language; duplicate matching can conflate recurring openings; more profile signals can overfit 209 exposure-biased decisions; a third equal RRF leg can over-amplify correlated scorer/structured facts; and changing embedding text invalidates active vectors. Fail-open parsing, shadow counters, reason-specific audits, time-split replay, RRF ablation, and automatic `text_hash` re-indexing (`scripts/rank_jobs.py:61-73`) contain those risks. I would not change the debate model yet: Sonnet is different from the Opus primary ranker (`config.py:7-11`; `ranker/debate.py:112-169`), its ±3 nudge/bottom demotion is bounded (`ranker/debate.py:190-225`), and no snapshot metric isolates its contribution. First compare no-debate/current-debate replays; only then test a cross-family reviewer on the same cases.

### 4. User-behavior grounding (explicit, not implicit)

**The seven dismissed items:** after this change, all seven become explicit calibration fixtures and durable direct-correction signals. The four absent-Python/Lead-title cases cannot appear as negative `cons` for PHP-core roles; the Magento, “legacy,” e-commerce agency, and product/SaaS-ownership dismissals likewise become neutral unless later behavior or a direct questionnaire answer contradicts them. Existing stored scores need not be bulk rewritten, but any newly scored or naturally fingerprint-invalidated job uses the rule; the frozen replay should rescore the seven cases and require removal of the dismissed con without forcing an artificially high overall score.

**Duplicate posting, different country, already applied (7+ occurrences):** before Sonnet, the current run is compared in memory with prior applied jobs available through the existing repository/API. A same-company, normalized same-role, near-identical-description mirror becomes `auto_rejected` with a duplicate reason when the earlier job was applied to; current-pool duplicates keep one canonical candidate (prefer candidate-eligible location, then newest) and reject the mirrors. Borderline matches are not rejected: they receive a negative facet score or are surfaced for review. This catches the real pattern without a new canonical-ID column, though it cannot offer durable cluster analytics and must recompute comparisons each run.

**Required spoken language:** a posting with explicit mandatory French, German, or Spanish is rejected before scoring if that language is absent from the candidate's B2+ questionnaire languages. The observed “connected to Russia” rejection is not a proficiency rule: handle it as a separate direct avoided-country/company-affiliation preference only when the candidate has configured that rule and the description supplies unambiguous evidence. A description merely written in another language can be treated by the existing collection language logic, not confused with a spoken-language requirement; “French is a plus” fails open. This is intentionally distinct from the present company-level `working_language` check (`evaluator/dealbreakers.py:201-219`).

### 5. Cost analysis — two separate numbers, not one blended estimate

**(a) One-time implementation cost.** Assuming one engineer familiar with Python and the API contract, estimate **7–10 working days**: 2–3 days for frozen replay/metrics and fixtures, 1.5–2 days for language/duplicate shadow gates, 1 day for scorer and distiller calibration, 1 day for the facet leg and ablations, 0.5 day for embedding expansion, and 1–2.5 days for review and shadow validation. No migration, re-extraction, or historical rescore is required. Re-embedding up to the 2,000 active-pool cap costs roughly **$0.10–$0.25**, derived from the real run's $0.003/91 embeddings and increased text length (snapshot §7), while optional fresh model evaluation is budgeted at **$5–$15**; retrieval-only replay is effectively $0. Because production usage summaries have not been recorded since 2026-08-30, actual implementation experiments must restore per-module logging before trusting a measured total (snapshot §7).

**(b) Ongoing day-to-day operational cost.** The historical baseline is ~$2.25 for a typical 91-job run and ~$3.14/100 jobs; $1.91 of that run (85%) was Haiku extraction plus Sonnet scoring/debate, while embedding and rerank together were only ~$0.0044 (snapshot §7). The facet leg, duplicate comparison, regex/language checks, replay metrics, and longer single-vector embedding add effectively **<$0.01/run**. Savings come only from scorer calls avoided before Sonnet. The snapshot does not say how many of a typical run's 91 jobs become auto-rejected or which of the 393/500 scorer-rejected jobs match the new deterministic rules, so I estimate a deliberately conservative **15–35% reduction in the Sonnet scorer portion**, not a 79% reduction in total cost. Using the historical $1.05 Sonnet scorer+debate line as an upper base and keeping debate mostly fixed yields approximately **$0.20–$0.50 saved/run**, or **$1.75–$2.05/day**, midpoint **$1.90**; current Sonnet 5 is cheaper than historical Sonnet 4.6, so both baseline and savings may be slightly lower in live billing (`config.py:65-72`; snapshot §7). Instrumentation should replace this range after two shadow weeks; if language/duplicate gates cover little of the 393 cases, quality still improves but cost remains near $2.25.
